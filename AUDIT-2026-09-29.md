Top findings:

## 2. HIGH

### H-1 (Critical if confirmed) [UNVERIFIED] Internal SECURITY DEFINER helpers may be client-callable

- **Where**
  - `supabase/migrations/20260829000000_set_aware_draws_and_live_rarity_validation.sql:142` (`grant_pack_contents(p_uid uuid, p_pack pack_types)`).
  - `20260826000000_server_minted_match_tickets.sql:127-131` (`grant_xp`, `grant_bp_xp`, `track_stat` take a uid).
  - `20260830000000_account_reset.sql:139` (`grant_inventory_pack(uid, pack, n)`).
- **Why it matters**
  - `create or replace function` preserves the existing ACL. This migration file carries no `revoke` for `grant_pack_contents`, although the same file does revoke and grant for `random_*`, `rarity_is_*` and `create_mystery_template`.
  - The 09-08 audit counts 78 SECURITY DEFINER functions callable by any `authenticated` user and says the list is "almost entirely legitimate player RPCs". Nobody has checked these helpers.
  - `grant_pack_contents` takes a composite `pack_types` argument, so PostgREST accepts a JSON object for it.
- **Failure scenario (if EXECUTE is granted to authenticated)**
  - `rpc('grant_pack_contents', {p_uid: <me>, p_pack: {slot_config:[{type:'x',count:500,rarity_weights:{Mythic:1}}], allowed_sets:null, foil_chance:1}})` grants 500 Mythics for free, or serialized prints.
  - `rpc('grant_xp', {p_uid:<me>, ...})` and `rpc('grant_inventory_pack', ...)` work the same way.
- **Fix**
  - Add `revoke all on function ... from public, anon, authenticated` for every helper that takes a uid. Grant only to `service_role`, or keep them callable only from other SECURITY DEFINER functions.
  - Better: make the helpers non-`security definer` internal functions in a private schema.
  - Verify with section 5, query A.

### H-2 [READ] Match rewards are farmable, and "bounded by real time" is false

- **Where**
  - `20260826000000_server_minted_match_tickets.sql:45-53` (begin_match: count then insert, no lock).
  - `:78` and `:96-97` (the 45s minimum age only).
  - `:108-112` (200/day cap).
  - `src/lib/supabase.ts:391-405` (docs claim "reward throughput is bounded by wall clock").
  - `src/App.tsx:505` (UI hides PvE from non-creators).
- **Why it matters**
  - The tickets are independent. There is no "one open match per user".
  - `p_won` is asserted by the client, and so is the fact that a match happened at all.
- **Failure scenario**
  1. A script calls `begin_match` 60 times at t=0. The count-then-insert check is racy, so concurrent calls can exceed 60.
  2. At t=46s it calls `record_match_result(true, id)` for each id. All succeed.
  3. That is 60 paid "wins" in under a minute, capped only by the 200/day ceiling. Every day that is about 200 × (100 credits + 60 XP + 50 BP XP), plus `wins` inflated for leaderboards and achievements, per account.
  4. The publishable key ships in the bundle and sign-up is open, so it scales by account.
  5. `App.tsx:505` gates PvE to `role === 'creator'`, but that is UI only. The RPC pair is live for every account.
- **Related**: when the 200/day cap is hit, `record_match_result` returns null after the ticket was already claimed (`:104-112`). The ticket is burnt for nothing and the client shows nothing (M-2).
- **Fix**
  - Server: allow at most one unredeemed ticket per uid, or serialize begin_match with `pg_advisory_xact_lock(hashtext(uid))`.
  - Add a per-uid minimum gap between redemptions.
  - Stop trusting `p_won` for currency. Until matches are server-authoritative, pay a flat amount that does not depend on it, or drop wins-based rewards.
  - Update the misleading comments.

### H-3 [READ] `reset_account()` re-opens reward claims and re-grants the Deck Box

- **Where**: `20260830000000_account_reset.sql:80` (`delete from player_achievements`), `:110-123` (`xp = 0, level = 1`), `:136-139` (`grant_inventory_pack(..., deck box, 1)`).
- **Why it matters**
  - The file's own comment says "there is no version of 'reset your account' that should include 'and also re-grant rewards you already collected'". The code does exactly that in three places.
  - Achievement `claimed` flags live in `player_achievements`, and the reset deletes them. The `player_stats` counters that feed them (`track_stat`) are not reset, so an achievement is re-completable and re-claimable, each claim paying credits, vouchers or a pack.
  - Level-up bonuses come back too. `record_match_result` returns `level_credits_bonus` and `level_vouchers_bonus`, and the reset sets level back to 1.
  - A new Deck Box is granted on every reset. The Deck Box holds a Leader plus a 60-card deck with 2 Super-Rares and 8 Rares.
- **Failure scenario**
  1. Claim everything.
  2. Trade the whole collection and credits to an alt account. Trades escrow nothing until accepted, so this is trivial.
  3. `reset_account()`.
  4. Re-claim the achievements and level bonuses and open the free Deck Box.
  5. Repeat weekly.
- **Side effects**
  - `delete from player_cosmetics` / `player_inventory` also destroys cosmetics and packs that Battle Pass claims paid out. `claimed_tiers` is preserved, so those tiers can never be re-claimed and the player loses the reward permanently.
  - SettingsScreen.tsx:302 tells the player that "daily login, Battle Pass, missions" are not touched but says nothing about achievements or cosmetics.
- **[UNVERIFIED] Possible hard failure**: `delete from mystery_pack_templates where owner` runs before shop-listing history is cleared. If `shop_listings.template_id` has an FK without ON DELETE, any shop owner with a past mystery listing cannot reset at all.
- **Fix**
  - Keep achievement claim state, or key claims by season and reset only progress.
  - Stop resetting level, or make `grant_xp` idempotent per level (a `max_level_paid` column).
  - Do not re-grant the Deck Box on reset, or only grant it once per account.
  - Do not delete cosmetics that were granted by claims.
  - Fix the copy in SettingsScreen.tsx.

### H-4 [PROBE] Units with a targeted "enters" effect cannot be invoked without a legal target

- **Where**
  - `src/game/v3/engine.ts:1968-1970`: `if (def.onInvoke && SINGLE_TARGETS.includes(...)) { targetIid = opts.targetIid ?? autoTarget(...); if (targetIid === undefined || !canTarget(...)) return false; }`.
  - `canInvoke` (`engine.ts:1919-1932`) does not check this, so it reports true.
  - The UI comment at `GameV4.tsx:2522-2531` says "Units and Items are deliberately NOT covered — they keep their body and bond value and only lose the rider". The AI agrees: `invokePriority` in ai.ts comments "A Unit is never disqualified for a dead ENTERS rider".
  - The engine does the opposite. `resolveInvokedCard` already handles the fizzled rider at `engine.ts:2053` (`!fizzles(...)`), which shows the intent.
- **Affected cards** (verified against POOL_V4, 297 cards): `ash_shaper_mystic` (anyTarget, so it can always go face), `bladetail_symbiont`, `blight_snarler`, `deceptive_angler`, `floating_jellyfish`, `gearbone_strider` (friendlyAny, so it can target the player), `grit_and_halftones`, `neon_phantom_assassin` (anyTarget), `scale_butterfly`, `skeletal_steed_rider`, `stag_of_the_cosmic_pyre` (anyTarget), `star_patterned_manta`, `the_pier_side_menace`, `wingbone_horror`. Ten of these are stuck when there is no legal target. Enemy-target riders can also fail when every enemy unit is Warded.
- **Repro [PROBE]**: fresh game, active player, Main1, empty field, `scale_butterfly` in hand with 9 of every essence. The probe printed `canInvoke true` and `invoke false`.
- **Impact**
  - Human: `GameV4.tsx:2680-2722` (`tryInvoke`) falls through to `doInvoke(cardIid, {})`, which calls `autoTapFor` first (locations exhausted, essence floating) and then gets "Can't invoke that right now." The INVOKE button was live.
  - CPU: `ai.ts` tries the card every main phase (`tapForCost` then `invokeCard` false), which can waste essence, and it never plays these cards into an empty board.
  - These outcomes feed the balance tables in docs/FULL_AUDIT_2026-09-08.md.
- **Fix**
  - In `invokeCard`, do not return false for Units, Items or Locations when the rider has no legal target. Set `targetIid` to undefined and let `resolveInvokedCard`'s `fizzles()` handle it. Keep the hard refusal only for Events, whose whole card is the effect.
  - Also make `canInvoke` and `invokeWhy` agree with the engine.
  - Add a test for `scale_butterfly` on an empty board.

### H-5 [READ] `media:sync` overwrites the lossless masters in `art-archive` with the shrunk copies

- **Where**
  - `scripts/migrate-art.ts:306-312` (the `fresh` filter) and `:331` (`fs.writeFileSync(dest, await getObject(key))`).
  - `.github/workflows/art-pipeline.yml:47-51` (weekly cron), `:97-98` (runs `npm run media:sync`), and the actions/cache restore of `art-archive`.
- **Why it matters**
  - The header says the archive holds the only lossless masters ("a webp derivative cannot be re-derived from without compounding the loss") and calls `sync` "Safe, additive".
  - After `shrink-originals` runs, the bucket object under each key is a small 1200px webp, while the archive holds the full-size original. Sizes differ for every image.
  - `phaseSync` treats "known key whose archive size != bucket size" as "replaced in place" and re-downloads it, overwriting the archive master with the shrunken webp. It then re-derives the ladder from the degraded source.
- **Failure scenario**
  1. Run full-migration. Archive = full-resolution PNGs, bucket = shrunk masters.
  2. The scheduled Monday `sync` sees every image as "changed", downloads the whole bucket again (billed egress, the thing the pipeline exists to cut), and overwrites all masters in the cached archive with lossy copies.
  3. The cache is saved under the new run_id. The old cache entry expires after its 7-day retention, so the lossless masters are gone.
  4. Same for a laptop run of `media:sync`.
  - `purge` and a second `shrink-originals` already refuse in this state because of the size check. Only `sync` mis-handles it.
- **Fix**
  - In `phaseSync`, treat a size mismatch as "changed" only when the archive is smaller than the bucket, or when the ETag or mtime differs.
  - Or record the shrunk size per key in the manifest after `shrink-originals`, and compare against that.
  - Never overwrite an existing archive file. Write a new `key.v2` next to it instead.
  - Until fixed, disable the `schedule:` trigger, and back up `art-archive` off-platform now.

## 3. MEDIUM

### M-1 [READ, mechanism confirmed in auth-js source] `Game` re-mints the match ticket on every auth event

- **Where**: `src/App.tsx:292-302` (`useEffect(..., [session])`), `src/meta/MetaContext.tsx:147-155` (`onAuthStateChange((_evt, s) => setSession(s))`).
- **Why it matters**
  - supabase-js 2.110.1 emits `SIGNED_IN` on every hidden to visible tab transition (`GoTrueClient._onVisibilityChanged` -> `_recoverAndRefresh` -> `_notifyAllSubscribers('SIGNED_IN', currentSession)`, at 4858). The session object is freshly parsed from storage each time. `TOKEN_REFRESHED` fires hourly.
  - `MetaContext` stores each one, so `session` gets a new identity and `Game`'s effect re-runs.
- **Failure scenario**
  1. Start a match. `beginMatch()` mints ticket A at t=0.
  2. The player tabs away during narration and comes back at t=100s. A second `beginMatch()` mints ticket B, and `matchIdRef.current = B`.
  3. If they returned within 45s of the game ending, ticket B is "too young" and the server returns null, which the client treats as "already recorded / no reward".
  4. Worse: `beginMatch()` failing (network, or "Too many matches started recently" after 60 tab-switches in an hour) resolves to `{matchId: null}` and `matchIdRef.current = matchId` overwrites a valid ticket with null. The error is dropped (`.then(({ matchId }) => ...)`), and `record_match_result` later raises "Missing match ticket".
  - Today only creator accounts and guests can reach a match, so the reward impact is limited to creators. It becomes user-facing the moment PvE opens.
- **Fix**
  - Depend on `session?.user?.id`, not `session`.
  - Never overwrite a good ticket with null. Mint once and retry only on failure.
  - Surface the beginMatch error.
  - Optionally memoize `session` in MetaContext by `access_token`.

### M-2 [READ] Silent reward loss when the server returns null

- **Where**: `20260826000000_...sql:96-112` returns null for too-young, expired (>6h), already-redeemed and daily-capped tickets, and `src/App.tsx:315-324`.
- **Why it matters**
  - The client treats `!error` and `!data` as "already recorded, or legitimately no reward" and returns. The game-over screen shows neither a reward nor an error.
  - For a genuine loss of reward (conceding under 45s, a stale ticket, or the 200/day cap after the ticket was consumed) the player is told nothing.
- **Fix**
  - Return a structured reason (`{status:'too_early'|'expired'|'duplicate'|'capped'}`) instead of null.
  - On the daily cap, do not burn the ticket (raise, or update `redeemed_at` only after payout).
  - Show the reason on the game-over screen.

### M-3 [PROBE] Clash labels mis-state incoming and dealt damage

- **Where**: `src/components/GameV4.tsx:3875-3884` (`incomingIfConfirmed`), `:3901-3915` (`clashFaceDamage`), `:3010` (`selectedMight`), and the pure label functions at `:1620-1670` that all take the resulting numbers.
- **Why it matters**
  - They sum `effMight` for unguarded attackers and compare it to Vitality. The engine also applies Doublestrike (face hit twice), the defender's Bulwark reduction per packet, Onslaught, and Overrun spill.
  - The file's own doc comment stresses that these labels must be exactly right on "the exact swing that ends the game".
- **Repro [PROBE]**: an unguarded 6-Might Doublestrike attacker against a 10-Vitality defender. The button reads "NO GUARDS — TAKE 6" with no LETHAL tag. `resolveClash` deals 12 (6 in the first-strike step and 6 in the normal step), the defender ends at -2, and the attacker wins.
- **Fix**: compute the label numbers with the same packet logic as `collectStepWithHistory`. The AI already has `faceDamage()` and `unguardedDamage()`, and one shared helper can serve both.

### M-4 [READ] `random_card_of_rarity` maps an unknown rarity to Mythic

- **Where**: `20260829000000_...sql:47-52`. `start_idx int := 1` is only overwritten on a match, and index 1 of `ladder` is `'Mythic'`.
- **Failure scenario**: a `pack_types.slot_config` or `roll_weighted_rarity` output with a rarity string not in the ladder (a typo such as "Super Rare", or "Leader") makes the draw start at the rarest tier, so packs pay out Mythics. The fallback direction is inverted.
- **Fix**: raise on an unknown rarity, or default `start_idx` to the last (Common) index.

### M-5 [READ] A slow or failed catalog fetch silently degrades the whole session to the bundled pool

- **Where**: `src/App.tsx:617-624` (`withTimeout(fetchCardTemplates(), 20_000, null)` then `if (templates) applyCardPool(...)`), `src/game/v3/engine.ts:513,517` (createGame throws on unknown ids), and `GameV4.tsx:1843` (the `useState` initializer that calls it).
- **Why it matters**: on a timeout or error nothing is shown, and the session runs on `generated-cards.ts`. Cards approved from Player Submissions since the last bundle sync are not in it.
- **Failure scenario**
  1. The player owns a Showcase card and has a saved, `is_valid` deck containing it.
  2. On a flaky start the fetch times out.
  3. The Collection screen (which iterates POOL_V4) does not show the card, and DeckBuilder reports "Unknown card".
  4. PLAY -> the custom deck -> `createGame` throws "Unknown card id" inside `useState`, and the `ErrorBoundary` shows "Something broke" with only a page reload as recovery.
- **Fix**: on a null fetch, show the retry screen when the account is signed in, or at least an offline banner. Have `deckDefFromCustom` and PlayScreen drop or flag decks that reference unknown ids instead of crashing.

### M-6 [READ] Mobile viewport and safe-area handling

- **Where**: `src/components/GameV4.tsx:4327` (`h-screen`, i.e. 100vh), `src/App.tsx:342`, and `index.html:8` (`viewport-fit=cover`). `env(safe-area-inset-*)` is not used anywhere in `src/`.
- **Why it matters**
  - On iOS Safari and Chrome Android, 100vh is the large viewport, so the bottom of the match board (hand dock and phase button) sits under the browser toolbar until the user scrolls the inner container.
  - With `viewport-fit=cover` and no insets, the home-indicator area (portrait) and the notch (landscape) overlap the hand dock and side controls.
- **Fix**: use `h-dvh` (or `100dvh` with a `vh` fallback) on the match root and the wrapper, and add `padding-bottom: env(safe-area-inset-bottom)` and side insets to the dock and headers. If the app is not meant to bleed under the notch, drop `viewport-fit=cover`.

### M-7 [READ] `fetchGradedCards` swallows errors and wipes the vault UI

- **Where**: `src/meta/grading.ts:282` (`if (error) return [];`), `src/meta/GradingScreen.tsx:143-150` (`reload`) and `:152-160`.
- **Why it matters**
  - Every other fetcher in supabase.ts throws so a failure does not look like "empty". This one returns [].
  - Any transient error after `submit` / `reveal` / `sell` / `crack` makes `reload()` call `setGraded([])`. The vault and the limbo list vanish, the pending countdown stops, and the player believes their slabs are gone.
  - CollectionScreen.tsx:129 has the same fetch and hides the shelf.
- **Fix**: throw on error, and keep the previous state in `reload`.

### M-8 [READ] `create_mystery_template` validation gaps

- **Where**: `20260829000000_...sql:375` (`p_mode not in (...)`), `:435` (`s->>'mode' not in (...)`), and `:409-427` (`value::numeric`).
- **Why it matters**
  - `NULL not in (...)` is NULL, so `p_mode = null` skips the mode check and takes the "advanced" branch. A slot with no `mode` key also passes.
  - `jsonb_each_text` values are not type-checked: `"NaN"` and `"Infinity"` cast to numeric, satisfy `> 0` and `< 0` is false, so the template is accepted with a NaN or infinite weight. The pack draw then produces NaN sums or exceptions.
  - The buyer is not charged (the transaction rolls back), but the seller can list an unsellable pack.
- **Fix**: `if p_mode is null or p_mode not in (...)`, use `coalesce(s->>'mode','') not in (...)`, and require `jsonb_typeof(value) = 'number'` with `isfinite`.

### M-9 [READ] No source of truth for RLS and RPCs in the repo

- **Where**: `supabase/migrations/` has 6 files. The docs cite ~128 RPCs and 37 tables.
- **Why it matters**
  - A fresh project cannot be rebuilt from the repo.
  - Findings such as H-1, H-3 and the `deleteDeck` policy claim ("confirmed correct" in a comment, 20260826:141-150) cannot be reviewed.
  - `create or replace` migrations rely on ACLs that are not written anywhere.
- **Fix**: dump the live schema (`supabase db dump`), commit it as a baseline migration, and add a CI check that greps for `security definer` functions without an explicit `revoke ... from public, anon` and grant.

- **L-7 [READ] `isMeteredStorageUrl` is a substring check.** `lib/media.ts:156-160` looks for `/storage/v1/object/public/`. `.../storage/v1/render/image/public/...`, `.../object/sign/...` and percent-encoded paths bypass the egress guard.
- **L-8 [READ] Approved art is a mutable hotlink.** `submissions.ts:151-156` and the server both accept any `https://` image URL. After approval the submitter can change the image at the remote host, bypassing moderation, or use it as a tracking pixel for every viewer. Consider rehosting on approval.
- **L-9 [READ] `publicUrl` uses `encodeURI`** (`scripts/lib/storage.ts:147-149`), which leaves `#`, `?` and `&` unencoded. A key containing `#` or `?` yields a truncated URL. (The 09-08 audit already flagged `:` in filenames.)
- **L-10 [READ] Silent row-count cliffs.** `fetchMarketListings` has `.limit(200)` (`supabase.ts:1035`) and the search box filters client-side, so listings beyond the soonest-ending 200 are invisible and unsearchable. `fetchCardTemplates` (`supabase.ts:248`) and the other unpaginated selects hit PostgREST's default 1000-row cap. That is fine at 297 cards, but a catalog above 1000 would silently truncate and trigger M-5.
- **L-11 [READ] Global Space/Enter shortcut.** `GameV4.tsx:2414-2435` clicks the primary divider button for any Space or Enter keydown on a target that is not a button, input or `role=button`. A focused `<a>`, `<summary>`, or `role=checkbox/tab/menuitem` element gets the game action fired as well as its own.
- **L-12 [PROBE] `finishDuskShed` has no phase guard** (`engine.ts:1646`). It is exported, and a stray or double call flips the turn again. I called it after a normal `endPhase` sequence and the turn passed straight back to the first player with no Dusk for the second player. The UI does not currently call it twice, but the engine should refuse unless `phase === 'Dusk'` and the shed is actually pending. The 09-06 audit's caveat that clash and window ordering is caller-driven still stands.

## Findings (ordered by severity)

### F1 [HIGH, economy] Grading is a large credit faucet (expected-value > 1 for most cards)
grading.ts:171-206 (GRADE_ODDS, GRADE_MULTIPLIERS, premium), economy.ts QUICKSELL_PRICES.
E[grade multiplier] = 3.835 (TCA/AMG), 4.612 (Keeper, P(10)=11.3% vs 4.3%). Times premium: TCA 6.14x, AMG 4.79x, Keeper 4.61x quicksell.
Numbers (expected slab quicksell vs quicksell + fee):
- Rare (100): TCA 614 vs 100+400; Keeper 461 vs 100+70 (net +291 expected/card); AMG at 10+ copies (fee 117) 479 vs 217.
- Mythic (3000): TCA 18,409 for a 400 fee (6.1x); foil Mythic (7500): 46,021.
- Keeper is EV-positive from Uncommon up (115 vs 95). Only Common is a sink.
Grade-then-quicksell mints credits from nothing; fee is a flat sink independent of card value. Fix: make fee proportional to base quicksell (e.g. >= 30-50% of it), or scale multipliers so E[mult]*premium <= ~1.0-1.3 net of fee, or route slab quicksell through the market not a fixed price. Design decision, but the numbers are the evidence.

### F2 [MED, stats integrity] `won` is client-asserted; abandoned/short matches never count
supabase/migrations/20260826...sql:82-135; App.tsx:311-341; GameV4.tsx:2295-2318.
- The ticket proves a match started >=45s ago, not who won. Any authenticated caller with a ticket can send p_won=true: wins/losses/win-rate (ProfileScreen.tsx:121, PlayerProfileModal.tsx:96), and win-based achievements are forgeable. Payout 100 vs 40 credits, xp 60 vs 25, bp 50 vs 20.
- Only a finished engine game reports. Menu-exit / tab-close mid-match records nothing, so win rate is survivor-biased. A concede under 45s: server returns null (no update matched), client treats null-without-error as "already recorded" (App.tsx:324 `if (!error) return`), so the loss is silently dropped.
- Daily cap check (`v_paid_today > 200`) runs AFTER the ticket is marked redeemed and returns null; those rejected tickets still count toward the rolling 24h window, so a player who keeps playing after 200 stays capped until 24h idle. Also off by one vs the "200" comment only in that the current ticket is counted (201st refused, so 200 pay: OK).
Fix: server-authoritative result (PvP spike), or at minimum count a ticket started-but-not-redeemed for >6h as a loss (cron), and return a distinct code for "too early" vs "already redeemed".

### F3 [MED, RNG / repro] Recorded seed cannot reproduce the match it labels
matchHistory.ts:32-45 (MatchRecord stores seed, labels, vitality only), GameV4.tsx:1847-1858, decks.ts:228.
- Comment claims "seed + decks + outcome", but decks are stored only as label strings. The CPU deck comes from randomArchetype() with default `Math.random` (decks.ts:228; App.tsx:277-278), unrecorded, so "quote an exact match" is impossible.
- `firstPlayer: rng() < 0.5` consumes the first draw of the match RNG BEFORE createGame, and firstPlayer is not stored. Replaying with createGame(..., {seed}) makes a fresh mulberry32 with no coin-flip draw, so every shuffle is shifted one draw and P1 may differ.
- Human mulligans (manual) also consume the stream and are unrecorded.
- Seed = `Date.now() % 2147483647` (GameV4.tsx:1847): 31 bits, ms-granular, so two matches in one ms share all shuffles; mulberry32 has 2^32 states vs 40!+ decks (fine for gameplay). engine.ts:506 `Date.now() & 0xffffffff` can produce a NEGATIVE seed that is stored on state.seed; mulberry32 masks with >>>0 so replay works, but matchHistory/bug reports show negatives.
Fix: store {seed, firstPlayer, both DeckDefs (leader+cards), human mulligan count, cpu archetype seed}; derive firstPlayer from a separate rng (mulberry32(seed ^ K)) so createGame({seed}) alone reproduces it; use crypto.getRandomValues for the seed.

### F4 [MED, likely economy drift] reset_account re-opens achievement rewards
20260830000000_account_reset.sql:~101 (`delete from player_achievements`), comment at 100-110 lists battle pass, missions, daily claims as deliberately NOT reset because "zeroing them would re-grant rewards" but achievements (which carry claimed flags and pay credits/vouchers, AchievementsScreen.tsx:149,324) ARE wiped. A player can claim every achievement, reset every 7 days, and re-earn them. Also `showcase_cards`, cosmetics, decks and graded cards vanish (intended). Fix: keep a `claimed_at` ledger (separate table) that reset does not touch, or keep player_achievements rows and zero only progress.

### F5 [MED, float drift] Client slab quicksell price can exceed server by 1 (conditional on numeric SQL)
grading.ts:236-245 `Math.ceil(quicksellPrice * gradeMultiplier * premium)`; also expectedSlabValue (Math.round, 214-222).
Exact-rational comparison over 528 rarity x foil x grade x service combos: 15 mismatches, all client = server + 1, from IEEE error before ceil. Examples: Rare, grade 5, TCA: 100*1.1*1.6 = 176.00000000000003 -> client 177, exact 176. Also Common foil g5 TCA 45 vs 44; Super-Rare foil g5 TCA 1321 vs 1320; Ultra-Rare g5 TCA/AMG/Keeper 1409/1101/881 vs 1408/1100/880; Alt-Art g5 TCA/AMG 3169/2476 vs 3168/2475. All at grade 5 (mult 1.1).
Fix: integer arithmetic. Store multipliers in tenths/hundredths (x100 ints) and premium likewise: ceil(base*m100*p100 / 10000) via Math.ceil((a*b*c)/10000) on integers, or Math.ceil(x - 1e-9).

### F6 [LOW-MED, float drift] deckAdvice 'high' threshold at exactly 30% is off
deckAdvice.ts:69 CURVE_TARGETS[2]+CURVE_TOLERANCE = 0.2+0.1 = 0.30000000000000004; 18/60 = 0.3 so `fraction >= ...` is false. Result: the "5+ cost" bucket needs 19/60 to read 'high' (31.7%) while its mirror 'low' triggers at 6/60 = 0.1 (0.2-0.1 = 0.1 exact), so the band is asymmetric (18 cards is not flagged; symmetric 6 is). The same expression in decks.ts:133 (`bucketCounts[b]/DECK_SIZE >= CURVE_TARGETS[b]+0.1`) lets the sim's builder take a 19th 5+ card. Fix: compare integers: count*10 >= (target*10+1)*ref/... or round: Math.round(x*1e6).
Also deckAdvice CURVE_TARGETS/tolerance are hand-mirrored (decks.ts exports neither): drift risk; export from decks.ts.

### F7 [LOW-MED, display vs server] Pack odds modal claims "exact server-side odds — no hidden weighting" but omits real behaviour
StoreScreen.tsx:~760, packodds.ts.
- Server adds a 1% per-pack serialized pull (grant_pack_contents `random() < 0.01`, set_aware_draws...sql:222-260) as an EXTRA card beyond card_count, weighted by remaining supply. Not shown anywhere in packOdds/expectedRarities.
- `guaranteed_min_rarity` is passed to roll_weighted_rarity server-side (sql:170) but slotOdds ignores it; shown weights are wrong whenever a weight sits below the floor (current data is consistent: foundation min Common, synergy min Uncommon, chase min Rare).
- Leader slots: server forces foil=false (sql:198-202) but slotOdds/packFoilChance count foilChance for them (packodds.ts:80-95), overstating "bonus foil" for any pack with a Leader slot and foil_eligible/foil_chance set.
- Legacy slots: client forces `count: 1` (packodds.ts:98) but the server honours `count` for legacy rows too (`coalesce(v_slot->>'count',1)`, sql:168), so a legacy row with count>1 is under-counted.
- Fallback ladder: rolled rarity with zero cards in the pinned sets falls DOWN (Alt-Art has 0 cards today, so the displayed Alt-Art odds, if any pack lists them, are really Full-Art).
- Per-card odds are not per-rarity odds: 8 Mythics vs 120 Commons means each Mythic is far likelier than each Common; not shown (design note only).
Fix: model the serialized pull as a footnote (1% x supply-weighted), skip foil for card_type=Leader, use count for legacy, apply guaranteed_min_rarity by zeroing/renormalising per the actual roll_weighted_rarity, and drop "exact" until parity is test-pinned against the SQL.

### F8 [LOW, bug] Theme validation via `in` accepts prototype keys
useTheme.ts:14 `saved in THEMES` is true for "constructor", "toString", "__proto__", "hasOwnProperty". applyTheme (themes.ts:170) then does THEMES['constructor'].colors.ink and throws inside the useState initializer, so a hand-edited or stale frycards_theme value white-screens the app on every load until storage is cleared. Fix: `Object.hasOwn(THEMES, saved)` (or a Set of names).

### F9 [LOW, stats] Simulation statistics: several places treat noise as signal
scripts/simulate-v5.ts, aggregate-cohorts.ts, leader-rank-stability.ts
- simulate-v5.ts:2527-2545 significance gate: Wilson CI of played-win% vs the in-deck win% as a fixed number. The baseline has its own sampling error and played-games are a subset of in-deck games (positively correlated), and ~300 cards are tested at 95% with no multiplicity correction (~15 false positives expected), plus |z|>=1.5 on residuals where variance is population (not sample) variance (2508). Use a two-proportion test on disjoint sets (in-deck-not-played vs played) with Holm/BH correction.
- simulate-v5.ts:2030-2036 pair sampling: `if (j===i) j=(j+1)%n` gives pair (i,i+1) twice the probability of any other j (biased sampling of seat-swap pairs, low impact). Sampling is with replacement; fix by drawing j from n-1 and shifting.
- Timeouts (MAX_TURNS=60, line 242) return null: leaderPair cells count game but no win for either side (2258-2272), so cell winPct sums < 100 and Leaders with slower kits are penalised. Report timeouts separately or count as 0.5.
- Seeds `Math.floor(pairRng()*1e9)+1` (2257): ~95k games gives ~4.5 expected seed collisions (birthday); harmless but use the full 32 bits.
- Seat-swap "paired seed" (2015-2050) pairs only the RNG stream, not the shuffle outcome (different decks in seat P1), so the pairing variance reduction is weaker than stated.
- aggregate-cohorts.ts:82-100,110: cross-cohort mean is an unweighted mean of rounded (0.1) winPct ignoring per-cohort game counts; NaN propagates if a Leader is missing from a cohort (?? NaN then reduce); "ONE-SIGNED" flag with 2 cohorts is true 50% of the time under the null and has no standard error; the lemon test uses the deck's own value inside the median it is compared to.
- leader-rank-stability.ts:118-119,143-152: comment says ranks are "distinct by construction", but means are averages of 0.1-rounded winPct, ties are plausible and sort order breaks them arbitrarily, so 6*sum d^2 is inexact. Ranks are computed over each draw's Leader set, then Spearman over the intersection (ranks not recomputed on the intersection). "Quotable if rank range <= 1" has no noise floor tied to games/Leader (pinned suite has 9 decks x 3 x 2 games per opponent).

### F10 [LOW] Deck code decode does not enforce color legality or minimum size
deckcode.ts:34-75: verifies leader type, id existence, per-rarity caps and DECK_MAX, but not `isColorLegal(card, LEADER_COLORS[leader])` nor DECK_MIN (60) nor ownership. An imported code can hold off-identity cards; check the builder revalidates on save. Encoding sorts with localeCompare (locale-dependent, harmless to decode but the code string for the same deck can differ per locale, breaking string-equality dedupe). Use plain `<`.

### F11 [LOW] Stats rounding / display
ProfileScreen.tsx:121, PlayerProfileModal.tsx:96 `Math.round(wins/games*100)`: 199/200 shows 100% and 1/1000 shows 0%; use floor for the top end (or one decimal). Achievement rows show `progress/target` unclamped (AchievementsScreen.tsx:360-367; bar is clamped, text can show 120/100).

### F12 [LOW] Test-hand tool is not the in-game deal
goldfish.ts:29-60: takes the FRONT slice of seededShuffle(cardIds, seed); the engine shuffles the leader-filtered deck in dd.cards order and deals by pop() from the END, after also consuming P1's shuffle first. Same seed is therefore never the same hand as the match's; the module doc ("seeded one can be quoted... in a bug report") oversells it. # S4 - Replayability audit (frycards)

Scope: (a) replay/spectate/review tooling, (b) replay value/retention. No bugs/perf/backend cost.
Effort: S <=2 days, M ~1 week, L multi-week. Evidence cites files read.

## Part A - Match replay tooling

### Ground truth (what exists)
- engine.ts: `mulberry32(seed)` (line 26), `createGame(..., {rng, seed, firstPlayer})`, `GameState.seed`, `iidCounter` on state (deterministic iids; comment says explicitly "precondition for deterministic replay"). Shuffles, mulligan, random Exhume all use `state.rng`.
- ai.ts: no randomness at all (`_rng` param in `maybeMulliganPlayer` is unused; no Math.random). The CPU is a pure function of state -> CPU moves need NOT be logged, only re-derived.
- GameState is NOT serialisable: holds `rng` closure (mulberry32 state not exposed), `chooseShed` callback, `telemetry` hooks. matchHistory.ts header says this outright and defers resume to the PVP_DESIGN action log.
- Engine is mutation-based, no `(state, action) -> state` reducer (PVP_DESIGN phase 1 says so). Actions are ~20 public functions (playWellspring, invokeCard, declareAttackers, declareGuards, passPriority, endPhase, mulliganHand, activateLeaderAbility, rebondItem, concedeGame, finishDuskShed...). No `Action` union type, no action log. `state.log: string[]` is human prose only (not machine-replayable). `dawnLog` likewise.
- `CpuTurnEvent` (ai.ts) is a structured event stream but CPU-only, with `logAt`. ROADMAP line ~597 claims "the engine already emits a structured event stream... so this is storage and a viewer, not new game code" - this is overstated: human actions are not in that stream, and it is UI-animation oriented.
- matchHistory.ts: localStorage key `frycards:match-history`, 50-entry ring. Record = {seed, finishedAt, won, turns, humanLabel, cpuLabel, humanVitality, cpuVitality}. Written from GameV4.tsx ~2294 on game over. `loadMatchHistory` has ZERO UI consumers (grep) - the data is write-only. Game-over screen shows "MATCH SEED n - TURN n" (GameV4 ~5844) as plain text.
- **Critical gap: seed does not reproduce the match.** Decks come from `randomArchetype()` / `buildDeck()` in App.tsx `setupToDeck` using unseeded `Math.random` (decks.ts:228 default arg); CPU deck likewise. Record stores only labels, not deck lists or leader ids. Custom decks can be edited/deleted later. So "quote seed in a bug report" identifies rng stream only, not the game. Also the human's choices (mulligan, shed, attackers, guards, response timing) shift rng consumption, so seed alone never replays anyway.
- GameV4 UI does its own rng draw (`firstPlayer: rng() < 0.5`) before createGame - must be part of the recorded setup contract.
- Deck sharing exists: deckcode.ts `FRY1:<leader>:<card*n,...>` encode/decode. goldfish.ts seeded test hands (`seededShuffle`). scripts/simulate-v5.ts headless CPU-vs-CPU; scripts/drive-match.ts Playwright driver with SEED0. No in-app replay/undo/spectate/analysis/share-link anywhere. No `#seed=` URL param; `seed` is a Game prop used by board-preview harness only.

### A1. Complete the match record (decks + setup)
- Current: seed + labels only; decks are Math.random-built.
- Proposal: extend MatchRecord with `humanDeck: {leaderId, cards[]}` (or FRY1 deck code string, reusing deckcode.ts), `cpuDeck` likewise, `firstPlayer`, `humanMulligan`, engine/rules version (CHANGELOG version constant), and `schema: 2`. Alternatively seed the archetype: `randomArchetype(mulberry32(seed^K))` so one number regenerates both random decks (only valid for quick match; custom decks still need lists). Store a code, not objects, to keep 50 entries small.
- Effort S. Deps: none. Risk: low; old records lack fields (migrate/filter). Rules-version drift means old replays can diverge after balance patches - stamp version and warn.

### A2. Human action log (the real enabler)
- Current: none.
- Proposal: define `type Action = {t:'wellspring',essence}|{t:'invoke',iid,target?,...}|{t:'attack',iids}|{t:'guard',assign}|{t:'pass'}|{t:'endPhase'}|{t:'mulligan'}|{t:'shed',iids}|{t:'leaderAbility'...}|{t:'concede'}`. Cheapest path that does NOT require the full reducer refactor: a thin `applyAction(game, actor, action)` dispatcher in a new file that calls the existing engine functions, and have GameV4 route human clicks through it while appending to `actions[]`. CPU turns are re-derived by calling `playTurn`/`respondToStack` at the same points (deterministic AI), or log CPU actions too for robustness against AI changes (recommended: log both, ~few KB/match; then replay does not depend on AI version).
- Effort M (GameV4 is 5.9k lines with many call sites; the seam is the risk). Deps: A1. Risk: medium - any UI path that mutates engine state without going through the dispatcher silently breaks replay; mitigate with a test that plays N seeded fuzz matches through dispatcher, then re-simulates from log and deep-compares final state (fuzz.test.ts / drive-match infrastructure exist). This same dispatcher IS PVP_DESIGN phase 1, so it is not throwaway.

### A3. Replay viewer / stepper / post-match review
- Current: none; game-over screen has only rewards, REMATCH.
- Proposal: `ReplayScreen` reusing the existing board renderer read-only: re-run createGame from record, apply actions[0..k], scrub bar + step buttons (turn/phase/action), plus prose `state.log` at each step. Reuse `CpuTurnEvent` animation path for the CPU segments. ### A5. Undo / takeback / mid-match resume

## 2. Findings, ranked by expected gain per effort

### P1. motion library (42.5 kB gzip, 129 kB raw) is eager but used by one lazy screen
- `motion/react` is imported in only two files: `src/App.tsx:18` (a `MotionConfig` wrapper) and `src/meta/GradingScreen.tsx:32`. GradingScreen has 4 `<motion.div>` and 3 `AnimatePresence`.

### P2. Startup is a serial network waterfall with no stale-while-revalidate
Boot sequence:
1. Load HTML, then JS.
2. `App` blocks on `fetchCardTemplates()` (App.tsx:611-628, 20 s timeout) before rendering anything but the splash.
3. Only then does `MetaProvider` mount (App.tsx:685). Its `getSession()`, `fetchShopItems()` and `fetchPackTypes()` (MetaContext.tsx:127-175) start after step 2 finishes. `loading = sessionLoading || assetsLoading` keeps the splash up until all three finish.
4. Then `useTheme` loads, and the lazy screen chunk is fetched last. A first-time visitor lands on `howtoplay`, which is another 21 kB chunk fetched only after step 3.

Total is about 4 sequential round trips (catalog, then session and store in parallel, then theme, then screen chunk). Each is 100 to 400 ms on mobile, so roughly 0.5 to 1.5 s of avoidable time to first interactive.

The bundled catalog (`GENERATED_CARDS`) is already in the bundle, and `cardpool.ts:2063` already builds a pool from it at import time.

Fixes:
- Render immediately from the bundled pool, then call `applyCardPool` and bump a version when the fetch resolves (or only block on a catalog version check).
- Mount `MetaProvider` in parallel with the catalog fetch, so session and store requests are not queued behind it.
- Do not block `loading` on the Store-only shop items and packs (MetaContext.tsx:157-175). They are already tolerant of failure (their own comment says so), so make them non-blocking.
- Kick off `import('./meta/HowToPlay')` or the likely next screen at idle, or put `<link rel=modulepreload>` for it.
- Expected gain: 300 to 1000 ms off time-to-menu. Effort: M. This touches boot semantics, so needs care with catalog overrides being applied late (see rebuild note below).

### P3. `CardFace` runs a forced-reflow layout effect on every render, with no memoization
- `FittedChips` (CardFaceV4.tsx:1715), `FittedRules` (:1804) and `FittedFlavor` (:1862) each call `useLayoutEffect` with no dependency array. Each reads `scrollHeight` and `clientHeight` after every render of every card, forcing synchronous layout.
- `CardFace` itself (:2206) is a plain function, not `React.memo`. Its props include inline `onClick`, `live`, `serial`, and `footer` nodes, so memo would need stable props.
- Costs by screen:
  - CollectionScreen renders every owned card in one list (see P5).
  - GameV4 re-renders the whole board on every engine event (see P4).
  - The 3D showroom re-renders at 60 fps (see P6).
- Fix (tiered):
  a. Add a dependency array (`[text, fontPx, maxLines, cap]`) to the three effects. Most renders then skip the reflow. (S)
  b. Wrap `CardFace` and `MicroCard` in `React.memo` with a custom comparator on `def`, `size`, `count`, `foil`, `dimmed`, `live` (value fields), `serial.number`. Callers must pass stable `onClick` (useCallback or a row-id dispatch). (M)
  c. Use a `ResizeObserver` or `document.fonts.ready` once per card and cache the result by `id|size` in a module-level Map. (M)
- Gain: I did not run a browser here. Judging from the code, this is the largest single runtime cost: each of about 300 collection cards does 3 reflows per render, and typing in the search box re-renders the whole list. Expect 3 to 10 times faster grid re-renders. Effort for (a): S.

### P4. GameV4 holds mutable engine state and re-renders the entire 4,000-line component per event
- GameV4.tsx:1843 keeps `g` (the engine `GameState`) in `useState` and mutates it in place. Every action calls `bump()` (:1908-1917), which does `setVersion(v => v+1)` and re-renders the whole component. The component has about 50 `useState` hooks (:1920-2074) and its body spans about lines 1779 to 5900.
- Only `ResolveDots` (:1088) is memoized. `BoardUnit`, `LeaderLane`, `LocationsLane`, `LocationTile`, `AbilityPill`, `PhaseStepper`, `HoverPreview`, `CardFace` are not, so a single bump re-renders every card on the board and in the hand, and reruns the reflow effects from P3. `useMemo` and `useCallback` are absent from the component (grep found none in GameV4 outside a comment).
- Hover state (`preview`, `previewPinned`, :2035-2036) and float and flash state (:2043-2045) live at the same root, so hovering a card re-renders everything.
- The CPU turn is narrated by beats, each of which sets several states, so one CPU turn can trigger dozens of full re-renders.
- Fix:
  - Snapshot the board pieces per render (`useMemo` keyed on `version`) and pass primitives or frozen snapshots to `React.memo`ed lanes and units.
  - Move hover preview and floats into small sibling components with local state, so hover does not reach the root.
  - Split the giant function into a reducer or store (`useSyncExternalStore`) so hand, board, log and stack subscribe to slices.
- Gain: I did not profile this. Expected 2 to 5 times fewer DOM and reconcile operations per interaction on mid-range phones. Effort: L (multi-day), but the hover extraction and lane memoization alone are M.

### P5. CollectionScreen and other list screens render everything; no virtualization
- CollectionScreen.tsx:690 renders `entries.map(...)`, one full-size `CardFace size='full'` (`standard` on narrow) per owned card and per foil and serialized variant. With the bundled catalog that is 297 cards, and each entry is a heavy DOM subtree (several hundred nodes with chips, popovers and gradients). The onClick is an inline closure. There is no `content-visibility`, `IntersectionObserver` windowing or pagination; `content-visibility` and `contain:` appear nowhere in `index.css`.
- The `useMemo`s at :153-376 are fine (they memoize the derivations), but any keystroke in the search box changes `filtered`, then `entries`, then re-renders all `CardFace`s (P3).
- Same shape in DeckBuilderScreen and PlayerShopsScreen (3,212 lines, 45 `.map`/`useMemo`, zero `React.memo`). Each of its 20 subcomponents is a plain function.
- Fix:
  - Cheap: add `content-visibility: auto; contain-intrinsic-size: <card w> <card h>` to the tile wrapper class. This gives a big win with no library, and images already use `loading=lazy`.
  - Then `React.memo` the tile and a `useDeferredValue` on the search string.
  - Optional: window with a small hand-rolled virtual grid (fixed-size tiles make this easy).
- Gain: initial paint and filter latency for a full collection 3 to 10 times faster. Effort: S for content-visibility, M for windowing.

### P6. 3D Showroom updates React state at 60 fps and re-renders the full card each frame
- `Showroom3D` (Card3DShowroom.tsx:548-580) runs a `requestAnimationFrame` loop that calls `onPose(setState)` every frame while spinning or coasting. The pose state lives in the parent (`ShowroomScreen.tsx:114`), so the entire screen tree re-renders per frame, including `<CardFace def size="full">` (line 676) with its layout effects (P3), plus `Motes` and `Backdrop`.
- The loop also keeps ticking forever (cheap when idle, but it never stops, even when the tab is hidden).
- Fix: keep pose in a ref, write `transform` and the rim-light style directly on refs in the rAF loop, and only commit to React state on pointer-up or when a UI readout needs it. Memoize the `CardFace` node with `useMemo`. Stop the loop when idle and restart on input, or on `visibilitychange`.
- Gain: takes the showroom from about 60 full re-renders per second to about 0. Effort: M.

### P7. Duplicate work and dead weight on the critical path
- `applyCardPool(GENERATED_CARDS)` runs at import (`cardpool.ts:2063`), and then again after the fetch (`App.tsx:620`). Measured: 297 cards, 135 ms for import plus first build in Node cold, 1.6 ms warm rebuild. So the double build is negligible; do not spend time on it. The bigger point is that `generated-cards.ts` (129 kB source, 31 kB gzip) is in the entry chunk. It holds 297 repeated 110-character Supabase URL prefixes and pretty-printed JSON.
  - Cheap fix: emit the fallback compactly (a prefix table plus arrays), or `import()` it lazily only when the fetch fails.
  - But P2 wants it immediately, so the realistic gain is about 10 to 15 kB gzip by shrinking the URL prefix. Effort: S to M. Not a priority.
- `@supabase/supabase-js` pulls all sub-clients: `storage-js` 106 kB and `functions-js` 16 kB source, neither used (`lib/supabase.ts` only uses auth, rpc, postgrest and channels). Building the client from `auth-js` and `postgrest-js` and `realtime-js` directly could drop roughly 120 kB of source, about 12 to 15 kB gzip. Effort: M, with some risk around the API surface. Low priority.
- `tailwind-merge` is 103 kB source, about 20 kB gzip, in vendor and used by `cn()` (`lib/utils.ts`). `cn` runs in every CardFace render, and tailwind-merge does some class parsing work per call (it has an internal LRU cache). Replacing it with `clsx` where no conflicting utilities are merged would save about 20 kB gzip. Effort: M (audit call sites). Medium-low priority.
- `lucide-react` is tree-shaken properly (48 kB source in vendor).

### P8. Image, video and font strategy
Good already:
- `media.ts` snaps widths to a ladder (160/240/320/480/640/960) and uses DPR-capped derivatives.
- The deploy workflow sets `VITE_ART_BASE_URL`.
- `SafeImage` and `CardArt` use `loading="lazy"` and an original-URL fallback.
- `VisibleVideo` defers bytes until visible, pauses when hidden, and uses `preload="none"`.
- Boot no longer preloads the entire catalog.
- Catalog: 297 images, of which 149 are PNG masters (about 6 MB each, per media.ts), 140 are webp, and 8 are mp4. Everything relies on the derived-webp pipeline being complete, otherwise the fallback fetches the master. That is an operational risk, not a code gap.

Gaps:
- No `<link rel="preconnect">` for the art and API origin (`dnngihsbqxccqvvedvjc.supabase.co`) in `index.html`. Saves one DNS+TLS handshake (about 100 to 300 ms) for the first catalog fetch and the first art. Effort: XS.
- Fonts are `font-display: swap` from self-hosted variable woff2 files (good), but nothing is preloaded. Fonts are discovered only after the CSS parses, so the first paint uses fallback text and then swaps. Add `<link rel=preload as=font type=font2 crossorigin>` for `montserrat-latin` (38 kB) and `space-grotesk-latin` (22 kB). Vite can hash the URL via an import, or add a small plugin. Effort: S.
- Images lack `decoding="async"` and `fetchpriority`. The above-the-fold hero (leader art on menu) is `lazy` like everything else. Add `decoding="async"` in SafeImage.tsx and CardFaceV4.tsx:1408 (XS). Optionally pass `eager` for the first few tiles.
- Videos have no `poster`, so a scrolled-in video card shows a blank box until data loads. Could use the derived webp of the first frame if the pipeline emits one. Effort: M (pipeline).
- VisibleVideo calls `.play()` on every visible video with no cap on concurrent playback. In the current pool that is only 8 mp4s, so it is fine today; note it for growth.
- The `preload.ts` boot-time gate is dead code (App.tsx comment says the preload was removed); confirm it is only used for in-screen batches and its 24-way concurrency is appropriate.

### P9. Context churn in MetaContext (small)
- MetaContext.tsx:381-408 builds a new `value` object on every render of the provider, with no `useMemo`. Every `setState` (profile, collection, decks, inventory, cosmetics; the realtime subscription refreshes them on a 350 ms debounce) re-renders all 30 `useMeta()` consumers, whether or not they read the changed field.
- In practice, mounted screens are few (one route at a time), so the cost is moderate; the risk is that an open CollectionScreen or PlayerShops re-renders wholesale on a profile realtime event (e.g. a credit tick).
- Fix: `useMemo` the value, and ideally split into 2 or 3 contexts (session/boot, profile, collection/decks) or use `useSyncExternalStore` selectors. Effort: S for `useMemo`, M for the split.
- Timers: only 9 `setInterval`/rAF sites in the app. Most are 10 to 60 s clocks. `GradingScreen.tsx:171` ticks every 1 s and re-renders the whole screen (1,066 lines) only to update countdowns. Isolate it into a `<Countdown>` leaf component. Effort: S. `MarketplaceScreen` (10 s tick) and `PlayerShopsScreen:1232` (30 s refetch) are fine (refetch cost belongs to the backend pass).

### P10. Engine and AI hot paths: no problem found
- The engine mutates state in place. No `structuredClone` or `JSON.parse(JSON.stringify())` exists anywhere in src (grep). The AI (`ai.ts`, 1,253 lines) is heuristic, one pass per decision, with no tree search and no state cloning.
- Measured: `npm run sim:v4 -- 4` ran 2,208 CPU-vs-CPU games in 21 s wall including startup, roughly 9 ms per full game (about 100 games/s). AI cost per turn is well under 1 ms. Engine and AI are not a UI bottleneck.
- Minor allocations: `engine.ts` has 40 `.filter/.sort/.find` and 16 spreads per call site, and `poolByType` and `poolHasKeyword` (`cardpool.ts:2069+`) re-filter the 297-card pool per call. These matter only if called per render (check DeckBuilder). Memoizing `poolByType` results (or building a `Map` by type once per `applyCardPool`) is an XS change with negligible but free gain.

### P11. PWA, caching and service worker: none exist
- No service worker, no manifest and no `<link rel=manifest>` (meta tags for iOS web-app exist). Hashed assets under `/assets/` are safe to cache immutably, but GitHub Pages serves `Cache-Control: max-age=600` and gives no control over headers. So a returning visitor revalidates (304) all 10 to 15 eager files every 10 minutes.
- Fix: a tiny hand-written service worker (precache app shell and hashed chunks, cache-first for `/assets/*` and for art derivatives, stale-while-revalidate for the catalog) or `vite-plugin-pwa`. It also makes the card catalog and art (the largest bytes, and the source of the egress problem noted in `media.ts`) survive across visits beyond the browser HTTP cache heuristics. Effort: M. Gain: repeat-visit load near-instant and offline shell.
- Also cache the catalog response client-side (localStorage or IndexedDB with a version) to fuel the P2 change.

### P12. CI and build time
- Local build: 5.4 s. Tests: 45 s (580 tests, 44 files; 53 s of test time, mostly the jsdom suites and fuzz). `sim:v4 -- 4`: 21 s. `npm ci`: 8.4 s. These are small.
- `ci.yml` job `checks` runs 9 steps serially (typecheck x2, lint, format, test, verify:pool, sim, build). Only the first `npm ci` is cached (setup-node `cache: npm`). Splitting typecheck+lint+format, test, and sim+build into a matrix or 3 parallel jobs would cut wall time to the slowest branch, about 1 min. The harness job installs Playwright Chromium and waits on the dev server; it can be gated to `main` or nightly if PR time matters. Effort: S.
- `deploy-pages.yml` re-runs `npm ci` and `npm run build` after CI already built once (it needs different env for `VITE_ART_BASE_URL` and base path, so a rebuild is legitimate, but CI's build step could use the same env and upload the artifact to be reused, removing about 30 s and a duplicate build). Effort: S.
- `package.json` lists `vite` in both dependencies and devDependencies, and `@vitejs/plugin-react` and `@tailwindcss/vite` under dependencies. Harmless for a static site but muddles installs; move to devDependencies (XS). Heavy devDeps (`playwright`, `@aws-sdk/client-s3`, `sharp`) inflate `npm ci` but not the bundle.
- Vite config has no `build.target` or `cssCodeSplit` tuning, no `rollup-plugin-visualizer`, and no size budget check. Add a size-limit check in CI to catch regressions like P1 (XS).
- `manualChunks` puts `react` (194 kB) in a separate chunk (good for caching). `vendor` is a catch-all; fine.

## 2. Grading is a money printer (critical)

**Current state**

- `grading.ts:157-171` sets the grade multipliers 1.1 to 12.0.
- `grading.ts:188-200` gives the odds over 94. The average multiplier is x3.835. Keeper's 55% half-point bump makes it x4.61.
- Payout is quicksell x grade multiplier x service premium (TCA 1.6, AMG 1.25, Keeper 1.0). The fee is flat (`grading.ts:75-103`).
- ROADMAP.md:653 already flags this as an open call.

**EV table** (`ev.py`, expected slab quicksell minus fee, non-foil):

| Raw card | Keeper (70) | AMG (180) | TCA (400) |
|---|---|---|---|
| Common (10) | -24 | -132 | -339 |
| Uncommon (25) | +45 | -60 | -247 |
| Rare (100) | +391 | +299 | +214 |
| Super-Rare (300) | +1,313 | +1,258 | +1,441 |
| Ultra-Rare (800) | +3,619 | +3,655 | +4,509 |
| Full-Art (1,000) | +4,542 | +4,614 | +5,736 |
| Mythic (3,000) | +13,765 | +14,202 | +18,009 |
| Foil Rare | +1,083 | +1,018 | +1,134 |
| Foil Mythic | +34,517 | +35,774 | +45,621 |

- Break-even raw price: Keeper 19, AMG 47, TCA 78. Anything Uncommon or better is +EV on Keeper.
- **Pack value with grading** (`ev2.py`, `cc.py`): a 499-credit booster is worth 560 by quicksell. If every Rare+ card is graded on Keeper it is worth about 2,076, or 2,129 taking the best of quicksell or grade per card. Even with instant grading (fee 350) it is about 1,477.
- That is a 3-4x return per pack. It is compounding and unbounded. Grading is time-gated at 16h standard, but nothing in the client shows a per-account queue cap.
- **Free reroll:** `crack_graded_slab` (`grading.ts:349`) returns the raw card with no fee refund and no fee shown at crack time. If cracking is free, a player can regrade until the grade is 9.5+. Keeper reaches 9.5+ with p=0.264, at about 265cr expected cost. A Rare then sells for about 620 and a Mythic for about 26,300. Verify `crack_graded_slab` in the live SQL for cooldown or one-time-grade flags.

**Proposal** (also fixes the roadmap open call)

1. Declared-value fee: `fee = base + pct x quicksellPrice(rarity, foil)`.
   - Keeper: 70 + 25%.
   - AMG: 180 + 30% (35% off the base fee at 10+ copies).
   - TCA: 400 + 35%.
   - Grade multiplier average is 3.83 to 4.61. A 30% fee gives an expected return of about 3.1x, so the mini-game is still +EV but bounded.
2. Rescale the grade curve so E[mult x premium] is about 1.15 (about 1.25 for TCA) rather than 3.8-6.1. New multipliers, for example: 5=0.35, 6=0.55, 7=0.8, 8=1.0, 9=1.4, 9.5=2.2, 10=5.0. Recompute with `ev.py`.
3. Crack: make it one-way per copy (a `graded_once` flag), or charge 50% of the fee, or make the card ungradable for 7 days.
4. Cap the queue at 20 slabs per account.
5. Separate "slab value" from "quicksell price": slabs should list on the market at market value only. Then a slab is a collector item rather than a faucet.

Effort S for the server SQL constants and mirrored constants. Risk: high player perception of a nerf, so migrate existing slabs at the old payout and grandfather them.

## 3. Pack value versus price (`packodds.ts`, StoreScreen)

**Current state**

- The fixture booster: 4 foundation, 2 synergy, 1 chase, 1 guaranteed foil, plus a per-slot foil bonus (0.0118).
- Quicksell EV per card: foundation 13.3, synergy 57.0, chase 208.2, foil slot 184.8. Pack total about 560.
- The daily free pack is 5 cards and worth 106.

**Issue**

- At a 499 price, buying and quicksell-ing everything returns 112% (`quicksell_cards`, `QUICKSELL_PRICES`). At 599 it is 93%. The live price decides whether packs are a faucet.
- The chase slot plus the foil slot are 70% of pack value. The foil slot alone is 33% of value and is 2.5x foil quicksell. Foil is priced as a x2.5 multiplier (`economy.ts:37`), which makes the guaranteed foil slot generous.
- Serialized roll is 1% per pack (`grant_pack_contents` line 222) on top of the 8 cards. Serialized cards cannot be quicksold, so they have no EV in these numbers.

**Proposal**

- Target pack quicksell EV at about 70% of price, for example 350-420 at 499. Lower the foil multiplier to x1.8 (`FOIL_QUICKSELL_MULTIPLIER`), or scale the foil slot weights down. The chase slot becomes the pack's identity.
- Add a duplicate-protection sink (section 4) so that value returns as dust or shards rather than raw credits.
- Show quicksell EV and "expected value vs price" in the odds modal. That is not currently shown. It is honest and builds trust.

Effort S (numbers), risk medium (needs live price data).

## 4. Duplicates, crafting, dust and pity (the biggest collection-experience gap)

**Current state**

- `grant_pack_contents` (`set_aware_draws...sql:206-210`) does a plain `quantity + 1` upsert. Packs never apply the copy cap (ROADMAP:637). There is no pity or bad-luck protection: `pity_note` on `pack_types` is display-only.
- "Shards" were removed from the game (`MainMenu.tsx:53`; `rarity.ts:29` comment is stale).
- There is no crafting, no dust and no trade-in. The only dupe outlet is a flat quicksell: Common 10, Uncommon 25, Rare 100, Super-Rare 300, Ultra-Rare 800, Full-Art 1,000, Alt-Art 1,800, Mythic 3,000 (`economy.ts:26-35`).
- Deck copy caps (`decks.ts:30`) are Mythic 1, Super-Rare/Full-Art/Ultra-Rare 2, others 4. A player who owns 5 Mythics can play one.

**Completion cost** (`cc.py`, booster at 499cr, coupon-collector, per rarity)

| Rarity | Cards | Packs to complete the rarity | Credits |
|---|---|---|---|
| Common | 120 | 186 | about 93k |
| Uncommon | 76 | 144 | about 72k |
| Rare | 46 | 131 | about 65k |
| Super-Rare | 12 | 141 | about 70k |
| Ultra-Rare | 6 | 144 | about 72k |
| **Full-Art** | 29 | **6,758** | **about 3.4M** |
| **Mythic** | 8 | **3,953** | **about 2.0M** |

- About 182 packs per Mythic pull and about 59 per Full-Art pull.
- Full-Art is 29 cards, at only 1.7% a pack. Casual income is about 3 packs a day, so one Full-Art takes about 20 days and complete Full-Art takes decades.
- Full-Art is 10% of the pool but is the wall. The set is not completable by pack alone.

**Proposal** (dust and crafting)

1. Add **Dust** as a soft currency. Extra copies beyond the deck cap can be dusted at: Common 1, Uncommon 3, Rare 10, Super-Rare 40, Ultra-Rare 100, Full-Art 120, Mythic 400. Craft cost is about 4x dust value: Common 4, Uncommon 12, Rare 40, Super-Rare 160, Ultra-Rare 400, Full-Art 480, Mythic 1,600.
   - Dust replaces credit quicksell for beyond-cap duplicates only, so credit inflation drops.
   - A duplicate Mythic (400 dust) is worth about 25% of a craft. A player needs about 4 dupes to craft one. That is fair.
   - Craft is a sink that is not credits, so it does not undermine grading or market pricing.
2. Add **pity**, tracked in `profiles` (or `player_pack_pity` keyed by pack type):
   - Guarantee a chase-slot Super-Rare+ after 10 packs with none.
   - Guarantee an Ultra-Rare+ after 30 packs.
   - Guarantee a Full-Art or Mythic after 60 packs without any.
   - Expected effect: Mythic per 182 packs falls to about 120, Full-Art per 59 to about 45.
   - Show a "next guarantee in N packs" bar in `PackOpening`/`StoreScreen`.
3. **Duplicate protection** for new cards: weight rolls 1.3x toward unowned cards within the rolled rarity (`random_card_of_rarity` currently picks `order by random()`). Cheap, and it is the single most felt improvement at the low tiers. At Common (120 cards) a full set falls from 186 packs to about 130.
4. Copy-cap auto-convert (ROADMAP:637): implement it as convert-to-dust, not credits, so the fifteen dead `converted_to_credits` branches in `PackOpening.tsx` become live. Or delete them.

Effort: dust and craft L (new table, new RPCs `craft_card` and `dust_cards`, new UI). Pity M. Dupe protection S (one SQL change). Risk: crafting mints cards outside the market, so gate it (Mythic craft capped at 1 a week, Full-Art at 3).

## 5. Bounty round trip (known, still open)

- `StoreScreen.tsx:1072`: buy at 3x quicksell, sell at 5x, max 3 sales a day, and the block is same-day only (ROADMAP:672).
- A Mythic gives +6,000 per round trip (9,000 buy, 15,000 sell). Three a day is 18,000 a day. Three Full-Art is 6,000 a day.
- This exceeds the entire casual income of about 1,450 a day. Bounty is the best faucet in the game.

**Proposal**

- Sell at 1.5x, buy at 2.5x, so there is no arbitrage (a buy-sell loop loses 1.0x).
- Also make "bought" permanent per card and per player, so a card cannot be bought and resold on a later day.
- Cap bounty sales at 2 a day above Rare.

Effort S (SQL constants plus mirror).

## 6. Match income and new-player ramp

**Current state**

- Start: 1,500cr + 25v is 3 boosters at 499 (about 2.5 at 599). The Deck Box gives a ready deck.
- First 60-card deck (`DECK_MIN` = 60, `decks.ts:17`) needs 60 non-Leader cards within the copy caps. The Deck Box helps, but the player then wants to upgrade. First week: about 10,000 credits, which is about 20 boosters, or about 3.5 Rares a pack-set.
- Level 50 unlocks shops. XP per win is 60, so level curve matters. The level table is server-side and not visible.

**Issues**

- Loss pays 40 and win pays 100. A bot that only claims wins can earn 20k a day. Legit players get about 760.
- The daily cap of 201 counts redeemed tickets, but the `> 200` check runs after the ticket is burned (`server_minted_match_tickets.sql:100-113`), so a capped player loses a ticket silently. This is minor.
- Nothing bridges the first 3 boosters and the first meaningful chase pull (about 59 to 182 packs).

**Proposal**

1. Split the reward: 100cr win, 40cr loss stays. Add a 5-win daily bonus of +250 and an 8-match diminishing schedule: matches 1-10 a day pay 100%, 11-30 pay 50%, 31+ pay 10%. Effective grinder cap falls from 20k to about 3.5k a day. Casual income is unchanged, because casual play is under 10 matches a day.
2. New-player pity: the first 5 packs opened by an account get the chase slot forced to Super-Rare+ on pack 3 and Ultra-Rare+ on pack 5 (a one-time flag on `profiles`, so `reset_account` should not clear it, matching how reset already leaves pity/streak fields alone).
3. First-week ramp: a 7-day "welcome" track on top of the login cycle (500cr on day 1, a Rare+ guaranteed pack on day 3, 1,000cr on day 7). New accounts only.
4. Server-authoritative results are the only real fix for `won` being client-asserted (PVP_DESIGN.md). Until then, throttle by the diminishing schedule above.

Effort: S-M. Risk: low.

## 7. Marketplace fees, floors and wash trading

**Current state**

- `MARKET_FEE = 0.05` (`supabase.ts:1021`), charged to the seller on completed sales.
- `MarketplaceScreen.tsx:694-700`: max 20 copies per listing, price from 1 to 1,000,000. Suggested price = quicksell price (`MarketplaceScreen.tsx:704`). Auction raise is 5% minimum (`minBidFor`).
- `get_card_market_value` returns `avg_price` only after 5 completed sales. `card_blended_reference` blends quicksell and market average and is used for shop soft-cap bands. Public listings have no reference band.

**Issues**

1. **No floor.** Listings can go below quicksell. Any card listed under quicksell can be bought and instantly quicksold by a second account. Two accounts (one selling at 1cr, one buying) is an item-transfer channel that costs almost nothing. Item transfer between alts already exists free via `create_trade`.
2. **Fee is small, so wash trading is cheap.** A wash trade at price P costs 5% of P. To move the average, five sales to the same account cost 5% of the total. The price feeds `card_blended_reference`, which drives shop soft caps. Manipulation of the reference price is therefore cheap.
3. **Fee is the only sink** and it is paid only by sellers who succeed.
4. **Listing cap of 1M** is about 330x the highest quicksell. It enables credit laundering between alts: a 1M listing bought by an alt is 950k transferred for a 50k fee, while `create_trade` lets cards move without any fee.

**Proposal**

1. Floor: minimum listing price = 60% of quicksell (`card_sell_price` x 0.6, x foil multiplier). This kills the "buy under quicksell and dump" arbitrage.
2. Cap: maximum listing price = 50x the blended reference, or 20x quicksell if no reference exists.
3. Fee: 5% base, with a 10% fee if the seller and buyer share a login IP or sign-up device fingerprint (backend cost aside, this is a simple flag) and a listing deposit (2% of price, refunded on sale) to make junk listing expensive.
4. Exclude wash-suspect sales from the average: ignore sales between accounts created within 24h, or repeated buyer-seller pairs (more than 2 in 7 days).
5. Trades: apply a fee-equivalent, for example a 3% credits tax or a cap of 10 trades a day per account, so trades are not a free market.

Effort S-M. Risk: sellers may complain about the floor, so pick 60%, not 100%.

## 8. Alt-art and foil progression

**Current state**

- Alt-Art exists everywhere (`rarity.ts`, quicksell 1,800, copy cap 1) but has 0 cards (ROADMAP:696).
- The ladder falls downward on an empty tier, so an Alt-Art roll would silently pay out a Full-Art. No pack weights Alt-Art.
- Foil is a per-copy `foil_quantity`, priced at x2.5 quicksell. There is no foil-upgrade path. The only route is the lucky foil slot.

**Proposal**

- Foil upgrade at the Grading Lab or a "Foil Press": 3 normal copies of the same card (beyond the deck cap) plus a rarity-scaled credit fee gives 1 foil. Cost per foil for a Rare: 3x100 quicksell value + 200 fee = 500, against a foil quicksell of 250. That is intentionally a value loss, so it is a sink and a collector path, not a faucet. Cap 1 a day above Rare.
- Alt-Art is the natural chase: add 8-12 Alt-Art cards as duplicates of the most-played cards (already designed as "separately-illustrated alternate printings"). Weight: 0.4% in the chase slot, replacing part of Full-Art's 1.3%. Allow a crafting route (2,400 dust) so it is obtainable.
- Until Alt-Art cards exist, hide Alt-Art from any player-facing chip or deck-builder filter.

Effort M-L (content plus RPC). Risk: low.

## 9. Serialized cards are a dead end

**Current state**

- `grant_pack_contents:222-270`: 1% per pack, weighted by remaining supply, inserts into `player_serialized_cards`. Caps (`supabase.ts:229`) are 75 Full-Art, 100 Ultra-Rare, 50 Mythic.
- Serialized prints are reserved: they cannot be quicksold or listed (`CollectionScreen.tsx:403-408`, `MarketplaceScreen.tsx:684-686`).
- A serialized Mythic /50 has no quicksell, no listing and no trade value other than showcase.

**Proposal**

- Allow serialized cards on `create_trade` and player shops, and on the market with a fixed floor (for example 10x the base quicksell for Mythic, 5x for others).
- Add an "Vault" quicksell for serialized cards at 5x base with a 30-day hold. It gives the pull a floor so the moment feels good.
- Add serial-number bonuses: #1-#5 and matching-digit serials (777, 100) get a small display badge and 2x vault price. This is a collection-experience feature and costs almost nothing.
- Track serialized remaining supply publicly. `get_serialized_feed` exists, and a "Remaining" counter on the Store makes the chase concrete.

Effort M. Risk: low.

## 10. Collection screen: goals, wishlists, binder

**Proposals**

Total payout is bounded and one-time, so it is safe against inflation.

## 11. Battle pass, achievements, submissions

**Battle pass** (`BattlePassScreen.tsx`)

- `BP_XP_PER_TIER = 100`. A win gives 50, a loss 20. Two wins per tier means 100 tiers a day are reachable at the grinder cap (201 wins). A normal season will be fully complete within a day for a bot and within about 2 weeks for a casual player at 10 matches a day (3 tiers a day at 60% wins: 6x50 + 4x20 = 380 XP = 3.8 tiers).
- Proposal: add a daily BP XP cap of 600 for match XP (6 tiers) and grant the rest via missions. Check `grant_bp_xp` for its existing cap, which is unseen. Effort S.

**Achievements** (`AchievementsScreen.tsx`)

- Rewards are credits, vouchers or a pack (`reward_credits`, `reward_vouchers`, `reward_pack_id`). One-time and bounded, so healthy.
- Opportunity: add collection achievements tied to section 10 (own 1 of every Rare, complete Volume #1 Commons, own a serialized card) and a "Grade a 10" achievement that pays a cosmetic instead of credits.

**Card submissions** (`CardSubmissionsScreen.tsx`)

- Players submit cards for the "Players Showcase 2026" set (`rarity.ts:20`). The set currently has zero live cards and its booster is inactive.
- Opportunity: pay the author a royalty in credits or vouchers per pack pull of their card (for example 1 voucher per 500 pulls), and an accepted-card bonus (500cr and a Showcase card in the collection). That gives creators a stake, and the payouts are tiny and bounded by pack volume.
- Risk: authors could farm pulls. Cap royalties at 20 vouchers a month per author.

## 12. Vouchers

- `VOUCHER_RATE = 100` (`grading.ts:25`). Vouchers are the premium currency and are earned free through level-ups, the login (5v weekly) and the BP.
- A voucher buys a pack at the same rate as 100 credits, so vouchers are not premium, just a second wallet.
- Grading in vouchers (`grading_voucher_fee`): Keeper is 1 voucher. With the grading EV in section 2, a voucher returns about 4.6x. If vouchers are ever sold for real money, this is an unbounded liability. Fix grading before any monetization.
- Proposal: keep vouchers non-tradeable (already true) and price grading in vouchers at 1.2x the credit rate, or disable voucher-paid grading.

## 13. Recommended sequence

1. **Grading fix** (declared-value fee, recalibrated curve, crack rules). Days. Highest inflation leverage.
2. **Bounty rates** and **market floor and cap**. Hours to a day. Closes the two arbitrage loops.
3. **Match reward diminishing schedule.** Hours. Caps the farm ceiling at about 3.5k a day.
4. **Dupe protection** (weighted unowned roll) and **pity counters.** 1-2 days. Largest collection-feel gain per unit of effort.
5. **Wishlist, set progress milestones and the duplicate view.** About 1 week. Adds collection goals.
6. **Dust and crafting**, then **foil press**, then **serialized vault.** 1-2 weeks. Bigger design, so do it after the sinks above are in place.
7. **Alt-Art content pass**, which is content work, not code.
8. Re-verify the live `pack_types` prices and odds and the SQL for quicksell, grading, bounty and BP with database access (not available in this audit). Rerun `ev.py` and `cc.py` with real numbers.

# 7. Supabase: cut log ingestion, storage size and cached egress, or move

Project `dnngihsbqxccqvvedvjc`, org `frycardv3`, Free plan, us-east-1, Postgres 17.

## Evidence limits
- Live DB unreachable (`28P01 password authentication failed`, advisors say hibernated). No live table sizes, row counts, query stats or advisor output. Figures below are from code, migrations, docs.
- Edge logs show `402` on `/rest/v1/`, `/auth/v1/health`. Per Supabase's Fair Use Policy, 402 = service restriction after exceeding Free quota (5 GB uncached + 5 GB cached egress, 1 GB storage, 500 MB DB). Restriction lifts at next billing cycle or on upgrade. Pausing does not erase usage already counted.
- Only 6 delta migrations are in the repo; the ~100 RPCs and most tables are not, so DB-side findings need the live schema.

## Where the bytes come from (code-grounded)
1. Storage `Card Images` ~1.02 GB: 153 PNG avg 5.9 MB, 140 webp ~740 kB, 8 mp4 ~5.5 MB. Already at the Free 1 GB cap. Originals serve if `VITE_ART_BASE_URL` unset or a derivative 404s (`media.ts` fallback).
2. Cached egress: art served from Supabase CDN. Cache-control raised to 30 days (migration 20260907), derivatives pipeline exists (`art-pipeline.yml`, weekly sync). Repeat visits are cheap, but every *first* visit by any player pulls art through Supabase, and fallbacks pull 6 MB originals.
3. Uncached egress (REST/Realtime/Auth):
   - `fetchCardTemplates` (`supabase.ts:250`) downloads the whole `cards.template` JSON column every app load, although a bundled catalog exists.
   - 20+ `select('*')` reads (`supabase.ts` 267, 287, 546, 815, 934, 1032, 1553...), incl. `achievements`, `pack_types`, `shop_items`, `friendships`, `market_listings`, `shop_listings`.
   - `MetaContext.tsx:343-350`: any change to `profiles`, `player_cards`, `player_inventory` triggers a full refetch (`refreshCollection` reloads the entire collection) after 350 ms debounce. Opening a 10-pack runs many row updates.
   - Realtime `postgres_changes` on 12 tables (`supabase.ts:42`): market_listings, shop_listings, player_shops, shop_purchases, friendships, trades, news_posts, serialized_supply, profiles, player_cards, player_inventory. Unfiltered subscriptions (market, shops, friendships, trades, news) fan every row change to every connected client, and each triggers a refetch. Each `postgres_changes` event costs an RLS check per subscriber.
   - `PlayerShopsScreen.tsx:1229-1232` polls every 30 s on top of realtime.
4. Log ingestion: Free plan logs are retained short-term and are not billed per GB, but PostgREST/edge log volume scales with request count, so cutting requests cuts logs. Nothing in the repo turns on log drains.

## Reductions, ranked by saving/effort

### A. Get out of the 402 now (unblocks everything)
- Wait for cycle reset, or upgrade to Pro ($25/mo, 250 GB uncached + 250 GB cached, 100 GB storage, spend cap ON by default). Cheapest way to lift restriction immediately. Then keep the spend cap on.

### B. Move card art off Supabase (largest, ~all cached egress + ~1 GB storage)
- Serve `derived/*` from Cloudflare R2 (no egress fees, 10 GB free storage, free CDN) or Cloudflare Pages/GitHub Pages static assets. The app already supports this: set `VITE_ART_BASE_URL` (`deploy-pages.yml`, `docs/ART_MIGRATION.md` "moving hosts").
- Only ~2 GB of masters need to live anywhere; derived set is small (30-70 kB per face). Keep masters in R2 or cold storage, delete from Supabase.
- Result: Supabase cached egress ~0, storage bucket ~0. This alone likely removes both the cached-egress and storage-size overages.
- Note: Cloudflare MCP failed to connect this session, so I could not check the account. R2 needs a bucket, public domain, CORS `GET`, and `Cache-Control: public, max-age=31536000, immutable` (the derived filenames are content-addressed, so a year is safe; the 30-day setting was a hedge for in-place replacement).
- Interim without moving: run the art-pipeline `full-migration` (`SHRINK`) so originals shrink; delete unused `derived` widths; make the 404 fallback not fetch originals for card tiers.

### C. Cut REST/Realtime egress (uncached, ~50-90% of DB egress)
1. Stop fetching `cards.template` at boot. Ship the catalog in the bundle (already there) and fetch only a `version`/`updated_at` row (or use ETag), refetching the full set only when changed. Saves the biggest repeated payload per session.
2. Cache static tables in `localStorage`/IndexedDB with a version key: `pack_types`, `shop_items`, `achievements`, cards. Refresh at most daily.
3. Replace `select('*')` with explicit columns; add `.limit()`/pagination on market, shops, friendships.
4. Make realtime payload-driven instead of refetch-driven: patch local state from `payload.new/old` for `player_cards`/`player_inventory` rather than refetching the whole collection. If refetching, fetch only the changed `card_id`.
5. Remove unfiltered realtime on `market_listings`, `shop_listings`, `player_shops`, `friendships`, `trades`, `news_posts`. Subscribe only while that screen is open (already per-screen mostly), filter by owner/user, or replace with a 30-60 s poll + pull-to-refresh. Drop the poll on shops if realtime stays; do not run both.
6. Use a single Broadcast channel or a tiny `notifications` table (per user) instead of many `postgres_changes` subscriptions: cheaper than RLS-evaluated change streams.
7. Batch pack-open writes into one RPC returning the new rows so the client doesn't refetch the collection.
8. Enable HTTP caching for public reads via a CDN in front (Cloudflare) for anonymous catalog endpoints, or bake `cards`, `pack_types`, `shop_items` into a static JSON file published by CI (the `sync-cards-db` script already exists in reverse). Then zero DB reads for static data.

### D. Storage/DB size
- Purge unused derivative widths and PNG masters once R2 holds them.
- In DB: check `pg_total_relation_size` per table once reachable. Suspects: `cards.template` (large JSONB per card), news posts, match tickets (`server_minted_match_tickets`: add TTL delete via `pg_cron`), auction/bid history, shop purchases, trades. Add retention jobs (delete tickets > 7 days, expired listings > 30 days), and `VACUUM`/drop unused indexes from the performance advisor.
- Store `template` as compact JSON, no repeated URL prefixes (also shrinks bundle `generated-cards.ts` 132 kB).

### E. Log ingestion
- Fewer requests = fewer logs (C above). Avoid `console`-style server logging in RPCs (`RAISE NOTICE`/`LOG`). Do not enable log drains (they bill egress). Keep `log_statement` at default. Avoid client polling of `/auth/v1/user` (`getSession` is local; do not call `getUser` repeatedly). Set `autoRefreshToken` normal but avoid multiple `createClient` instances.

## Cheaper/better backend: options
Suitable only if the ~100 RPCs (economy, market, grading, auth) can be ported; that is the real cost, not hosting.

|---|---|---|---|
